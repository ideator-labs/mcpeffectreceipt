CLAIM TO PROVE
A side-effecting MCP-style tools/call with a durable idempotencyKey ledger does not double-execute on retry. Unguarded retry doubles the side effect. Same key + same args replays the stored receipt. Same key + different args conflicts and does not execute.

CORE DATA SHAPE (implement this first)
File: src/receipt.py (or equivalent)

EffectReceipt:
  key: str                  # idempotencyKey from the client
  tool: str                 # tool name, e.g. "charge"
  args_hash: str            # stable hash of canonical JSON args
  status: str               # one of: in_progress | completed | conflict
  result: dict | None       # tool result when completed
  created_at: str           # ISO timestamp

Ledger operations (SQLite file at data/ledger.sqlite):
  begin(key, tool, args) -> Proceed | Replay(result) | Conflict | InProgress
  complete(key, result) -> None
  # begin must persist in_progress BEFORE the side effect runs (write-ahead)

SIDE EFFECT FOR THE DEMO
A fake charge tool that appends one line to data/charges.log and returns {"charged": amount, "tx": n}.
The mutation is the append. Count lines in charges.log to prove multiplicity.

demo.sh MUST:
1. Reset data/ (empty charges.log, fresh ledger.sqlite)
2. Run PATH A (unguarded): call charge(10) twice with NO key. Expect charges.log has 2 lines. Print "PATH A (unguarded): PASS" or FAIL.
3. Reset charges + ledger again for fair PATH B? Or use a separate amount. Prefer: reset only charges.log and ledger between paths so each path is isolated.
4. Run PATH B (guarded same key): call charge(10) with key=k1, then retry charge(10) with key=k1. Expect exactly 1 line in charges.log, second call returns same result (replay). PASS/FAIL.
5. Run PATH C (conflict): after PATH B state OR fresh: call charge(10) with key=k2, then charge(25) with key=k2. Expect still 1 charge for k2's first call, second returns conflict and does NOT append. PASS/FAIL.
6. Print a final summary. Exit 0 only if A,B,C all PASS.
